# 5. State machines and synchronous execution

The group asked that every driver be a state machine (to be discussed) and that drivers be synchronous. This chapter states what that means concretely and where the remaining choices are.

## Three state machines

A driver deals with three separate kinds of state. Keeping them apart is what makes drivers comparable and testable.

| Machine | Owned by | States | Visible as |
|---|---|---|---|
| **Engine lifecycle** | Shared contract, driven by the driver | `Loading → Unpaired → Pairing → Paired`, `KeyRejected` | `Engine::state()`, `Event::StateChanged` |
| **Therapy** | Shared contract (`TherapyMachine`), fed by the driver | Four independent regions: mode, basal, bolus, extended | `TherapyState`, `Event::TherapyChanged` |
| **Protocol / link** | Driver, private | Whatever the protocol needs: connecting, authenticating, selecting a setting, waiting for a frame, … | Not exported |

### Therapy machine (shared, current)

`TherapyState` has four regions that change independently:

| Region | States |
|---|---|
| `mode` | `Unknown`, `Off`, `Suspended`, `Running` |
| `basal` | `Unknown`, `Scheduled`, `Temporary { rate, duration }` |
| `bolus` | `Unknown`, `Idle`, `Immediate { requested, delivered }` |
| `extended` | `Unknown`, `Idle`, `Running { amount, duration }` |

Drivers change it only through `Transition`s (`Suspended`, `BolusStarted`, `LinkLost`, `Observed(state)`, …). The allowed transitions are defined once in `pump-shared` and drawn in [`therapy.mmd`](https://github.com/u-osaid/pump-shared/blob/main/.docs/therapy.mmd) (generated by `cargo xtask graphs`, so the diagram cannot drift from the code). An invalid transition is a `TransitionError`, which is a driver bug.

`TherapyMachine::guard(command)` refuses commands that make no sense in the current state (for example `Resume` when not suspended), the same way for every driver.

Rules:

- A driver MUST NOT keep its own copy of therapy state; it applies transitions to the shared machine.
- A driver MUST apply `LinkLost` when the link drops mid-bolus or mid-extended bolus, so those regions become `Unknown` until observed again.
- A driver SHOULD apply `Observed(state)` after each status read, so the machine re-synchronises with the device.

### Protocol machine (private)

The protocol machine is the driver's own business, but it MUST:

- be fully driven by the `Engine` inputs (no hidden timers or threads);
- have a bounded number of steps per command (the harness fails an engine that never settles);
- have a defined state after every possible `Completion`, including `Failed`, `Timeout` and `Disconnected`.

## Synchronous execution

"Synchronous" means **the public API is synchronous and poll-based**:

- every `Engine` method returns immediately;
- the engine never needs an async runtime, a thread or a callback from the host;
- the host may be as asynchronous as it likes (Kotlin coroutines, Swift concurrency, Embassy), but it feeds results back with plain calls.

This keeps bindings trivial (no futures across FFI), lets the same engine run on a microcontroller, and makes tests deterministic.

### Internal style: explicit enum or private `async`

There are two ways to write the protocol machine inside a driver:

| Style | Pros | Cons |
|---|---|---|
| **Explicit state enum** (`enum Step { Connecting, Authenticating { .. }, … }` with a `match` per input) | Every state is visible, nameable, serialisable and checkable by model checkers; easiest to review | Long multi-step flows become verbose |
| **Private `async fn` polled by the engine** (**Current** in `pump-ypso`: the engine holds `Pin<Box<dyn Future>>` tasks and polls them itself; each await point yields an `Action`) | Multi-step protocol flows read top to bottom like the spec | States are implicit; harder to inspect, persist or formally verify; needs careful handling of drop/cancellation |

Both satisfy the requirement, because neither leaks async to the host. **Proposal:** allow both, with these conditions for the `async` style:

1. No executor, waker or runtime crate; the engine polls its own futures.
2. Futures never outlive the engine and are dropped cleanly on `stop()` and link loss.
3. Safety-critical state (counters, therapy state, what was sent) lives outside the futures, in plain fields, so it can be inspected and persisted.

This is listed in [14-open-questions.md](14-open-questions.md#q3-internal-state-machine-style) for a final decision.

## Time

- **Monotonic time** (`Timestamp`, host milliseconds) drives protocol timeouts. The engine asks for a wake-up with `poll_timeout` and is told the time with `handle_timeout(now)`.
- **Wall-clock time** (`UtcTime`) is only given when needed (`handle_wall_clock`), for clock sync and history conversion.
- Engines MUST NOT read a clock themselves. This is what lets the harness run hours of virtual time in milliseconds.
